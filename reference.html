ORE (Open Real Estate) — format reference for LLMs

This is the complete definition of the ORE .ore file format, version 0.1.0, assembled as a single document you can read or author from. ORE is an open, JSON-based format for commercial real estate underwriting data, for any property type.

How to use this document

  • Reading a .ore file: it is standard JSON. Every field name spells out its units (clearHeightFt, amountPerSF, ...Percent) and conventions are declared in the file (e.g. baseRent.unit), never inferred. You can reason over a .ore file directly. Do NOT compute a multi-year DCF by hand — arithmetic over monthly cash flows is the engine's job, not yours; see "Calculation" below.
  • Authoring a .ore file: produce one self-contained JSON object conforming to the schemas below. formatVersion, property, and rentRoll are required; every other module is optional. Validate your output against the JSON Schema and run it through the reference engine before trusting any computed figure.

Core rules

  1. A deal is a SINGLE self-contained .ore file. Modules are top-level keys of one JSON object, never separate files. Calculation assumptions travel WITH the data.
  2. formatVersion must be 0.1.0 (semver; this document defines 0.1.x).
  3. Optionally include a root $schema URL so any reader resolves definitions from the file alone: "$schema": "https://oreformat.org/schema/0.1.0/ore.schema.json".
  4. Dates are ISO 8601 (YYYY-MM-DD). Money is USD. Percentages are percent values (3.5 = 3.5%) except ratios documented as decimals. Areas are square feet; land is acres.
  5. The file carries INPUTS ONLY. Outputs (NOI, DCF, IRR) are never stored in the file; they are produced by a conforming engine from the inputs.
  6. A field the schema does not define is an ERROR: never invent a field name. If you need to keep something the format has no field for, put it in a key starting with x- (e.g. "x-acme-dealCode": "D-41") on the object it describes. Every reader ignores x- keys, so they never change a number; if the value should change the math, say so in notes instead.
  7. Lease-up and later rollovers can use different leasing profiles. A space's profile prices the first lease generated for it; set rolloverProfile on that profile to name the profile for every expiry after that (e.g. a 24-month lease_up profile rolling into a 9-month general one).

Calculation

ORE ships an open-source TypeScript reference engine that consumes a .ore file and produces NOI, monthly/annual cash flows, direct cap and DCF value, debt schedule, levered/unlevered IRR, and sensitivity — with a first-class warnings array naming any simplification or estimate it applied. Conformance is defined by golden-file tests: a conforming implementation reproduces locked expected outputs exactly. When an LLM needs a number from a .ore file, call the engine (or the forthcoming @ore-format/mcp server) rather than computing it yourself.

Scope (v0.1)

US property of any type: set property.propertyType to what the property is. NNN/NN/modified-gross/gross leases. The valuation module carries inputs for all four approaches (DCF, direct cap, sales comparison, cost); the v0.1 engine computes DCF and direct cap. The engine is deepest on industrial and names, in a property_type_coverage warning, what it has not modeled for other types. Not yet modeled: retail percentage rent, office load factors and gross-up, hotel operations, international conventions, debt waterfalls.

Property that is not industrial

  • Office, retail, medical office: write leases exactly as for industrial. Omit physical fields that do not apply (clear height, dock doors). If the source has percentage rent, parking income, or a load factor, put it in the lease or property notes: there is no structured field yet, and you must not invent one.
  • Multifamily, student housing, self-storage, manufactured housing: there is no unit mix in the format yet. Write ONE LEASE PER UNIT: baseRent.unit: "total_per_month" with the unit's monthly rent, reimbursement.structure: "gross", escalation.type: "none", the unit number in suite, and a spaceType naming the unit type (one_bed, two_bed). Give each unit type a leasing profile with a 12-month term; market rent is stated per square foot, so divide the monthly market rent by the unit size. Vacant units go in vacantSuites. Set property.physical.unitCount. Identify residents by unit ("Unit 2A resident"), NEVER by name. Put other income (parking, laundry, fees) in rentRoll.notes until the format has a field for it. If the source gives only a unit-mix summary and no unit-level rent roll, write one lease per unit at the average rent for its type and say so in rentRoll.notes.
  • Outside the US: addresses must currently be US. Say so and stop; do not force a foreign address into US fields.

After you write a file: check your own work

A file can validate and still be wrong. Models extracting from an offering memorandum tend to drop the hard parts without saying so. Before you hand over a file you authored from a source document, do all four:

  1. Reconcile against the source. Show a table of file versus source for: suite or unit count, total leased SF, annual base rent, total recoveries, total operating expenses, and NOI. Give both numbers and the difference. For each mismatch, say whether you misread the source or the source disagrees with itself.
  2. Account for the commonly dropped items. For each lease, state whether the source mentions: free rent, renewal or termination options, expense stops or base years, expense caps, a security deposit, unfunded tenant improvements or commissions. "Not mentioned in the source" is an acceptable answer. Silence is not.
  3. Disclose authorship. Fill provenance: who or what generated the file, when, and every source document with its date.
  4. Do not invent assumptions. If the source gives no discount rate, exit cap, or market rent, leave that module out and say so. Do not supply your own.

Human specification

ORE Specification

ORE (Open Real Estate) is an open, JSON-based file format for property-level underwriting data. A .ore file is standard JSON — cat deal.ore | jq just works — validated against the published JSON Schema in schema/, then against the cross-field rules in validation.md.

  • Current format version: 0.1.0 (pre-release, unstable until tagged)
  • Schema dialect: JSON Schema draft 2020-12
  • Scope: US commercial property of any type, DCF and direct capitalization. The reference engine is deepest on industrial; coverage for each property type is in coverage.md

All v0.1 modules are drafted. property and rentRoll are required in every file; the rest are optional so a file can carry exactly what its producer knows (e.g. a broker may omit valuation and let the buyer add their own assumptions). A deal is always a single self-contained .ore file — modules are sections of one JSON document, never separate files.

Conventions

  • A .ore file is JSON. Any JSON parser reads it and any JSON tool works on it. The extension says which format the JSON follows; the content is plain UTF-8 JSON with no comments or trailing commas. Where a tool refuses an unknown extension, name the file deal.ore.json: every ORE tool accepts both. Serve it as application/json.
  • Dates are ISO 8601 (YYYY-MM-DD) strings.
  • Names: field names are camelCase (leasedSF, discountRatePercent). Enum values are snake_case: lowercase words joined by underscores, with acronyms lowercased (fixed_percent, per_sf_per_year, percent_of_egr, nnn, dcf). Digits may follow a word (year1, trailing12). A value may depart from this where it must match an external standard or data format, such as the ISO 3166 country code US.
  • Self-description: files may carry a root $schema URL pointing at the published schema, and field names spell out their units (clearHeightFt, ...Percent) — a reader (human, tool, or LLM) should understand a .ore file cold, with no external lookup. See docs/design/llm-and-excel.md.
  • Money is USD. Per-SF rent units are declared explicitly per lease via baseRent.unit — never inferred from market convention.
  • Percentages are expressed as percent values (3.5 = 3.5%), except ratios documented as decimals (e.g. coverageRatio).
  • Areas are square feet; land is acres.
  • Calculation assumptions travel with the data so any conforming engine reproduces identical outputs from the same file.

Unknown fields and extensions

A field the schema does not define is an error. Every object in the schema is closed (additionalProperties: false), so a misspelled or invented field fails validation instead of being silently ignored. A reader can trust that every field in a valid file means what the data dictionary says.

Extensions go in x- keys. Any object except a keyed map may carry extra keys whose names start with x-, with any JSON value. Use them for data the format has no field for yet: an internal deal code, a CRM id, a note a producer wants to keep next to the value it describes.

"leases": [{ "leaseId": "L-100", "x-acme-crmId": "T-4471", "...": "..." }]

The rules:

  • Readers ignore them. Validators accept them; engines never read them. An x- key cannot change any computed number, and the conformance tests check this by adding one to every object in every example.
  • Name them after the producer, x-<producer>-<name>, so two producers' extensions do not collide.
  • Keep them on save. A tool that edits a file should write back the x- keys it read, unchanged.
  • Not in keyed maps. The keys of marketAssumptions.leasingProfiles are profile names, so an x- key there is rejected; put it inside a profile.
  • Not a way to change the math. If an extension would need to change how a number is computed, it is a format proposal: open an issue.

lease.baseRent

Contractual base rent as a stepped schedule. Each step applies from its startDate until the next step's startDate, or until expirationDate for the last step. Steps are in ascending date order; steps before asOfDate may be omitted.

Field Type Definition

schedule[] (R) array Steps of { startDate, amount }, min 1.

Why an explicit unit? Rents are quoted per unit per month for apartments, and industrial rents are quoted per-SF-per-month in some markets and per-SF-per-year in others. ORE never infers the convention — the file states it, so every engine computes the same cash flow.

lease.escalation

Rule for generating rent steps not enumerated in baseRent.schedule. If the schedule enumerates every step through expiration, omit this or use type none. When present, engines apply the rule starting one frequency-interval after the last enumerated step's startDate, through expiration. Enumerated steps are always authoritative over generated ones.

Anchoring mid-lease escalation anniversaries. Because generated steps are timed off the last enumerated step's startDate, a rent roll struck mid-lease anchors correctly by dating that step at the most recent escalation date (not asOfDate) with the current rent. Example: current rent $15.68/SF/yr, last bumped September 2025 on a 12-month cycle — a schedule step of {"startDate": "2025-09-01", "amount": 15.68} puts every future bump on the lease's true September anniversary. Institutional rent rolls state this as a "first/next review date"; this pattern carries it without a dedicated field.

The reference engine models renewal options: at the lease's expiry the renewal branch of rollover uses the option's stated rent (fixed or percent_of_market, capped at market — a rational tenant won't renew above market) and renewalTermMonths, instead of the generic market-leasing assumptions. marketAssumptions.leasingProfiles.<spaceType>

At each lease expiration, engines blend the renewal and new-tenant outcomes by renewalProbabilityPercent.

A space's profile (its spaceType, or the first profile) prices the first lease generated for that space: the lease-up of a vacant suite, or the first rollover of an in-place lease (both of its outcomes). If that profile sets rolloverProfile, every rollover after that first generated lease uses the named profile instead. Underwriters usually keep these apart: a lease-up profile with long downtime and first-generation TI and LC, and a general profile for every expiry after that.

"leasingProfiles": {
  "lease_up": { "downtimeMonths": 24, "renewalProbabilityPercent": 0, "rolloverProfile": "general", "...": "..." },
  "general":  { "downtimeMonths": 9,  "renewalProbabilityPercent": 75, "...": "..." }
}

Validation rules

Validation rules

JSON Schema checks the shape of one value. The rules below check relationships across fields. The reference engine implements them in lint(). Any conforming implementation — including a Python port — produces the same results.

A result has:

Field Meaning
code Rule id from the tables below. This is the conformance id.
severity error — the file is invalid. warning — a default or fallback still produced a result; it does not by itself fail validation.
path JSON Pointer (RFC 6901) to the offending value. Omitted only when the whole document is the problem and no pointer applies; not_object uses /.
message Human-readable detail. Wording is not part of the conformance contract.

Results follow the file: structural checks, then each lease (required fields, duplicate leaseId, spaceType, excludedExpenses, options, rent steps), then vacant suites, then duplicate expenseIds, then each leasing profile's rolloverProfile (in profile order), then excludeExpenseIds, then taxReassessment.expenseId, then unrecognised enum values (in the order of the enum table, and within a row in file order), then unused leasing profiles (in profile order), then warning-level advice. Option fields on a non-renewal are reported in the order renewalTermMonths, renewalCount, rentBasis, fixedRent, percentOfMarket, then terminationFee when that field is present on a non-termination.

Conformance fixtures live in engine/golden/invalid/. Most are invalid; a fixture whose expected issues are all warnings (e.g. space-type-without-profiles) locks a warning-level rule. Each *.ore file has a sibling *.lint.json listing the code, severity, and path that lint() must produce, in order, and nothing else. schemaValid says whether the file also passes JSON Schema. Reference and id rules are schema-valid on purpose: JSON Schema cannot check them. Option rules are also expressed as if/then in the rent-roll schema, the same way escalation requires rate or amount, so a schema-only check rejects them too.

Omitting spaceType is not an error. A space with no spaceType uses the file's first leasing profile. Omitting taxReassessment.expenseId is not an error either: it defaults to the real_estate_taxes item.
